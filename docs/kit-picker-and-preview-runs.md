# Kit picker and complete preview runs

The standard creation flow is Style → Kit → Generate preview. A generation
produces a preview image and paint plan. The total comes from the active palette,
specification and HD price rules; the user sees only the combined price.

## Kit selection

Step 2 reuses the Step 1 illustrative palette strip. Custom or unmapped styles
display their description instead of invented HEX swatches. Advanced finish,
weathering and mood defaults resolve through the existing StyleIntent helper.
New works are private; publishing stays in Library.

`kitPicker.browse` searches names, normalized model identifiers, aliases, grades,
scales, series and manufacturers. Different filter dimensions intersect; values
inside one dimension are ORed. Drawer edits are drafts until Show kits is pressed.
Quick grade controls share the applied grade state. Tags support lookup and
curated type mapping but are not exposed as navigation.

The server returns 18 cards per page. The current infix search/facet implementation
uses bounded reads of up to 5,000 kit and base-unit records and 1,000 series records.
An external search index or denormalized indexed catalog is needed beyond this
bound. It does not fetch the full kit catalog into the creation page. Featured is
the initial catalog selection, not a claim of measured popularity. Recent comes
from owned creation records; Favorites uses the owner-scoped kitFavorites table.

Kit portraits reuse thumbnailAssetKey. Admin supports an HTTPS image URL or public
R2 object key with preview and removal. Use a 4:5 neutral canvas, one consistent
three-quarter view, low saturation, full model visible at approximately 70–80%
frame height, and no packaging or complex scene. Assets are configured, not
generated by this feature. Missing images are explicitly labelled Portrait pending.

Desktop uses an adaptive compact grid with a sticky preview panel. Mobile keeps
the total and Generate action in a fixed bottom bar. Advanced options use a sheet
so expanding them cannot push the desktop Generate action below the viewport.

## Generation reliability

creationRuns stores the owner, request key, frozen input, quoted cost, attempt,
stage references and final status. Starting a run atomically validates the quote,
reserves the total and creates a palette job. Each server-scheduled action runs
one stage, then atomically queues the next. Closing the browser does not interrupt
execution. Create and Library subscribe to the latest owned run.

Only one complete preview may be active per owner. Replaying a request key reuses
the same run; changing its inputs is rejected. Stage helpers receive a server-only
prepaid flag and do not create extra credit debits. A terminal failure refunds
the entire run once. A 25-minute watchdog refunds abandoned runs. Late text/image
results are guarded by the run's active attempt. A completed image wins over a
late watchdog and prevents a false refund.

Retry reserves the original total again after its prior refund. Successful
palette/specification stages are reused, while failed text compositions and image
jobs get fresh attempt references. Successful runs are not retried. Historical
spray plans, rendered resources and visual-palette separation remain intact.

No new environment variables are required. Deploy the generated schema/functions
using the normal Convex development command; existing records need no migration.

## Verification

Backend tests cover quote changes, insufficient funds, duplicate requests,
owner-only retries, one-time refunds, late attempts, stage reuse, account-scoped
favorites, alias search, grade/scale separation, archived kits and bounded pages.
Authenticated browser tests cover style continuity, Kit selection, filter drawer,
favorites, the unified output and the mobile Generate bar without paid inference.
