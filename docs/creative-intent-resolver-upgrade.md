# Creative Intent Resolver 与配色契约升级方案

日期：2026-10-11
状态（更新于 2026-10-12）：Style 核心部分已完成开发验收，已知渲染细节偏差记录在 [Style 升级实施记录](./style-upgrade-implementation.md)；Custom Kit 尚未实施。本文保留设计语义，字段示例用于设计讨论，不代表生产接口已发布。
关联方案：[Custom Kit 与参考图创作](./custom-kit-reference-architecture.md)。
统一执行顺序：[Style 与 Custom Kit 升级执行计划](./creation-upgrade-execution-plan.md)。

## 1. 目标与问题

创作链路需要保留用户意图，同时允许用户修改预设风格。两个案例暴露了不同问题：

- Sazabi / Arctic Ops：用户通过 Notes 要求蓝白配色，但预设、角色和材质的优先级高于 Notes。
- EVA / Rainbow：上游可以表达多种主要颜色，下游以单色角色槽位接收，无法完整表达多色装甲。

上述案例来自本次讨论；本文对根因的核对基于当前仓库代码，没有重新读取生产用户记录。

升级前实现证据（2026-10-11）：

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `convex/creativeContracts.ts`：Palette 与 Specification 模板 | Style / Material 高于 Notes | 明确的用户审美要求可能被预设覆盖 |
| `convex/creativeContracts.ts`：`assertExactRoles` | 每个角色必须恰好出现一次 | 同一装甲角色无法承载多个颜色条目 |
| `convex/creativePipeline.ts`：`complete` | Palette 与 Specification 均校验角色唯一性 | 仅修改提示词或扩大数组不能解决阶段转换问题 |
| `convex/paintRecommendationEngine.ts` | 油漆匹配 Map 以 `roleSlug` 为键 | 重复角色会覆盖匹配，需要同步更换关联标识 |
| `src/components/library/LibraryDetailPage.tsx` | 按角色寻找第一条匹配与部位记录 | 多色角色需要新的展示关联方式 |
| `convex/prototypeTools.ts` | Render 同时接收原始 Style Intent、Specification 和 Palette | 原始预设仍可能重新引入已被覆盖的颜色 |

`visual-palette.v2` 的数组本身并非固定六项；实际容量限制来自角色唯一性、提示词和下游按角色关联的整体契约。

## 2. 设计原则

1. **有效创作意图不能在阶段转换中静默丢失。** 颜色的删除、替换或用途变化，必须来自明确覆盖、用户批准的简化，或可解释的限制。
2. **Style 是创作起点。** 用户可以修改颜色，保留风格的视觉组织、材质语言和情绪；未被覆盖的默认要求继续有效。
3. **颜色集合与装甲角色解耦。** 角色数量不限制颜色数量，多种颜色可分布在同一个角色，一种颜色也可跨越多个角色。
4. **来源与约束强度分开。** AI 推测、风格默认和用户明确输入不能因为最终值相同而失去来源区别。
5. **视觉目标与油漆商品继续分离。** 缺少合适 SKU 时提供自定义混色或匹配说明，不用商品色域反向改写目标颜色。
6. **几何默认保留，授权修改另行表达。** 目录机体默认保持现有结构；Custom Kit 的用户明确结构修改应作为独立约束，不被无条件的原始几何锁覆盖。
7. **Kit 来源与适用性独立明确。** 官方目录 Kit 与用户 Custom Kit 共用下游契约，但保留各自来源、身份与版本；Custom Kit 首版使用单张参考图加文本，须先通过机体适用性判断，无关主体不进入主生成。

## 3. 架构与职责

```text
Style + 结构化用户要求 + Material + Mood + Weathering
                         ↓
             Deterministic Intent Resolver
                         ↓
                  有效意图契约
                         ↓
                    AI Palette
                         ↓
                  Palette 验收
                         ↓
                 AI Specification
                         ↓
               Specification 验收
                         ↓
                    AI Render

批准的 Palette → 确定性油漆匹配 → Paint Recommendations / Paint Plan
```

不新增 Agent，不引入自动任务规划或工具调用循环。Resolver 是数据合并和裁决逻辑，不调用模型。

对 Custom Kit，输入先经过一次 Vision Scan，扫描同时返回适用性和结构观察；服务端确认适用后才能形成有效 Kit Intent 并进入 Resolver。不将普通动物等范围外图片改造成机体，也不要求原创机体匹配官方 IP 或目录。双参考图与 donor 部件迁移暂不实施。

自然语言归一化与 Resolver 分开：前者理解表达，后者合并结构化要求、判定冲突、保留来源。可以复用已有 Style Interpreter；预设风格加自由 Notes 的路径是否增加一次模型调用，需要在实施前评估。有限语法解析也可用于第一版，但无法识别的要求必须保留并显式处理，不能静默忽略或假装已经解析成功。

`untrusted` 表示输入不能修改系统任务、输出协议和执行规则，不表示用户审美意图低于风格默认。

## 4. 约束模型

| 级别 | 语义 | 示例 |
| --- | --- | --- |
| `hard` | 必须满足；冲突或无法满足时报告问题 | 用户明确要求的颜色、部位、比例；未授权改变的结构 |
| `soft` | 尽量满足；偏离时记录原因 | 风格默认颜色、视觉层次、推荐部位、推测比例 |
| `free` | 该维度允许创作，仍受其他约束限制 | 未指定的装甲分色、局部装饰、视觉平衡 |

约束应作用于具体属性，而不是把整份 Style 或整个颜色对象一次性设为 `hard`。`free` 更适合作为某个维度的创作权限。

| 用户输入 | 强约束 | 可创作部分 |
| --- | --- | --- |
| `blue and white color combination` | 蓝白在目标涂装中明显呈现 | 深浅、比例、未指定部位 |
| `70% blue armor, 30% white armor` | 颜色和装甲范围内的比例目标 | 未指定的具体分色位置 |
| `blue chest armor` | 蓝色及胸部位置 | 未指定的色值和其他部位 |
| 明确 HEX | 指定的目标色值 | 未指定的比例与位置 |

颜色存在、色系、HEX、比例、视觉重要性和部位分别建约束。说 blue 不代表锁定 AI 选择的某个 HEX；列出两种颜色不代表各占 50%；指定颜色也不自动代表禁止其他颜色。

需要区分颜色修改的语义：新增、替换、保留、排除，以及“只允许这些颜色”的范围。禁止附加颜色不能自动扩大到骨架或传感器，除非用户表达覆盖这些范围。

## 5. 冲突与覆盖规则

按属性裁决，避免简单的全局来源排序：

- 机体与产品边界构成系统约束；Custom Kit 明确授权的结构修改在其作用范围内放宽几何保留要求。
- 用户明确指定的颜色、位置和比例覆盖相关 Style 默认。
- 用户主动选择的材质、旧化等覆盖对应风格默认；自动填充的默认选择需要保留来源，不能被当作主动选择。
- Mood 可以影响氛围和视觉组织，不能删除或改变强约束颜色。
- Notes 与用户主动选择发生同属性冲突时，只有明确的修改关系或可靠的操作顺序才能自动覆盖，否则记录冲突。
- 两条有效强约束无法同时满足时，不自动降级任何一条。

例如“保留肩甲形状”与“加厚肩甲”需要判断具体保留范围；不能让通用几何锁直接取消用户明确的局部修改。

Resolver 输出应包含有效约束、被覆盖要求、裁决记录与未解决冲突。只有可执行的契约进入生成阶段。

## 6. 颜色与部件分配

建议使用独立、严格、带版本的数据契约：

| 数据 | 主要内容 | 标识 |
| --- | --- | --- |
| Color Palette | 颜色名称、目标 HEX、涂装效果、来源约束 | `colorId` |
| Panel Assignments | 颜色引用、用途角色、现有部位、遮盖说明 | `assignmentId`、`colorId` |

六种现有角色可继续作为用途分组：`primary-armor`、`secondary-armor`、`inner-frame`、`accent`、`markings`、`sensor-color`。但必须区分：

- 视觉重要性：主要颜色、次要颜色、局部强调。
- 涂装用途：装甲、骨架、传感器、标记等。
- 具体部位：胸部、肩甲、前臂、背包等。

`primary-armor` 和 `secondary-armor` 本身仍包含视觉主次语义，不应代替具体部位标识。第一版可用清晰的部件组，不要求建立完整的三维面板数据库。

一个角色可以有多个 assignment；一种颜色可以被多个 assignment 引用。无需强制每台机体都具有所有六种角色，例如没有标记时不应强行生成标记颜色。

宽松的是表达容量，Schema 仍需严格。不能以 `any`、任意文本或无限重复项代替正式契约。颜色数量上限应来自经过验证的产品和性能边界，不能来自角色数量。

## 7. 比例与可见性

比例至少记录：计算范围、目标值、来源、强度。推测比例不得升级成用户明确比例。

建议第一版以外装甲涂装面积作为主体配色的默认规划范围；骨架和传感器独立处理。标记往往覆盖底色，是图层关系，不能简单与装甲底色一起累加至 100%。不同范围的比例不可直接比较或自动重标定。

没有明确比例时使用定性可见性要求，如“明显呈现”“主要颜色”“局部点缀”。AI 可以分配规划比例，但必须标记为 AI 分配。

规划目标与最终图片验收分开：契约可以准确保留 70:30，单张图片中的像素比例还受视角、遮挡和生成效果影响。没有几何面积或图像分析依据时，不承诺精确的最终面积比例。

比例容差、局部范围与整体范围之间的计算规则，留待契约定稿。

## 8. 来源、快照与阶段权限

来源记录应作用到属性层级，至少包含：

- 约束 ID、目标属性和作用范围。
- 来源类型：用户明确输入、用户主动选择、风格默认、扫描观察、AI 推测或系统规则。
- 原始字段或输入引用。
- 被覆盖约束与裁决原因。
- Resolver 版本、输入快照和有效契约版本。

AI 的 `rationale` 是解释，不是可靠的来源证据。必须能区分“用户要求蓝色”和“AI 自行选择这个蓝色 HEX”。

Palette 在允许范围内创作；批准后成为后续阶段冻结的颜色依据。Specification 分配部位，不重新解释或修改已批准的颜色。Render 执行有效结构、颜色和部位要求。

所有阶段使用同一份有效意图快照。原始 Style 和 Notes 保留用于追溯；传给下游的执行上下文不能重新包含已被覆盖的冲突指令。

输入键需要考虑契约、Resolver 和有效 Kit 的版本，使结构、配色或裁决规则变化不会误复用旧 Palette。历史生成继续绑定历史快照。

## 9. 验收闭环

Palette 验收：

- 所有有效必需颜色都存在，标识唯一。
- 色系、精确色值、涂装效果与明确比例符合各自约束。
- 无静默删除、替换、合并或新增不允许的颜色。

Specification 验收：

- 每个 assignment 引用有效颜色和部位。
- 应用于装甲的颜色不能仅靠传感器或标记“完成保留”。
- 明确部位要求与结构修改保持有效。
- 颜色比例及其计算范围没有被改变。
- 强约束违反时拒绝结果；软约束偏离时记录原因。

Schema 和引用检查可以确定性完成。自然语言描述是否真正匹配结构，以及图像是否正确执行，不能仅凭 JSON 合法宣称已验证。

## 10. 实施顺序与兼容性

1. 定稿有效意图、颜色、assignment 与来源契约，以及验收用例。
2. 实现 Resolver，修正模板优先级和有效输入编译。
3. 升级 Palette / Specification，并加入跨阶段验收。
4. 将油漆匹配与 UI 关联从角色唯一键切换到新标识。
5. 更新 Render 输入，消除旧 Style、Notes 和通用几何锁的冲突。
6. 保留旧版读取；新记录使用新版契约，禁止兼容投影静默压缩多色信息。

建议采用新的契约版本，例如 `visual-palette.v3`；最终命名在定稿时确定。已有 `palettePlanJson` 的兼容投影必须标记其表达边界，多色信息不能通过旧版消费者无声丢失。

升级前油漆匹配器使用递归组合搜索；实施中已改为按独立颜色寻找兼容目录样本，复杂度为 O(颜色数 × 目录样本数)。此次升级属于中等规模的生成契约与下游消费者改造，Resolver 本身保持轻量。

## 11. 回归案例

| 案例 | 预期 |
| --- | --- |
| Arctic Ops + 明确蓝白要求 | 蓝白生效，保留未被覆盖的风格语言，不擅自固定比例 |
| 70% 蓝色装甲 / 30% 白色装甲 | 保存装甲范围的明确比例目标 |
| 七种颜色，无用户简化要求 | 全部保留；多个主要颜色可同时用于装甲 |
| 绿色明确用于大面积装甲 | 不能只分配到传感器完成要求 |
| 用户只指定 blue，没有 HEX | 保留蓝色色系，允许选择合适深浅 |
| 选择哑光，同时明确要求高光 | 记录同属性冲突或明确覆盖关系 |
| Style 默认红色，用户要求仅蓝白装甲 | 原始红色被显式覆盖，不从下游 Style 再次回流 |
| 油漆目录无匹配 | 保留视觉目标，提供混色或无法匹配说明 |
| Custom Kit 明确加厚肩甲 | 局部几何修改生效，其他结构默认保留 |
| 普通小动物参考图 | 在 Kit Scan 适用性阶段拦截，不进入 Resolver 或主生成 |
| 动物形机甲或未知 IP 原创机体 | 按可见机体结构判断，适用时作为 Custom Kit，不强制官方目录身份 |
| 旧版作品 | 使用原有快照正常读取，不强制重写历史 |

## 12. 后续独立清理

`convex/catalogHierarchy.ts` 的 EVA 种子包含 `green chest accents`，应改为几何描述，例如 `chest accent panel geometry`。这证明种子数据存在颜色与身份混合，不能单凭该字段认定它导致了历史案例。

Style 实施中已完成种子及旧快照进入提示词时的窄范围清理；没有重写历史数据库记录。
